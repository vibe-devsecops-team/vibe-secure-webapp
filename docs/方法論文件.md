## 一、標準 Prompt 範本

### 1.1 需求轉化四步驟（撰寫 Prompt 前的準備）

寫出好 Prompt 的前提，是先把模糊的需求結構化。對齊指引第 2 節：

1. **需求拆解**：把使用者意圖拆成功能模組（如：登入驗證、資料查詢、UI 組件），一次只處理一個模組。
2. **技術選型**：確定框架與函式庫（本專案固定為 Flask + PostgreSQL + SQLAlchemy），要求 AI 遵循最佳實踐。
3. **規格定義**：寫清楚資料流向、邊界條件與錯誤處理邏輯。
4. **指令編譯**：把規格與品質/安全約束組合成最終指令，明確禁止 AI 自由發揮。

### 1.2 標準 Prompt 範本（每次生成模組時套用）

使用時只需替換「任務」一行，其餘維持不變，確保每次生成都帶著相同的安全與品質基準。

```
# 角色
你是一位重視資安的資深 Python 後端工程師，熟悉 Flask 與 PostgreSQL。

# 任務
請實作：［一句話描述單一模組，例如「一個讓使用者用 email 登入的 API 端點」］

# 技術規格
- 框架：Flask
- 資料庫：PostgreSQL，透過 SQLAlchemy ORM 存取
- 設定值（資料庫帳密、密鑰）一律從環境變數讀取，禁止寫死在程式碼中
- ［視模組補充資料流向、邊界條件、錯誤處理邏輯］

# 安全要求（必須全部遵守）
- 所有資料庫查詢必須使用參數化查詢或 ORM，禁止字串拼接組 SQL
- 對所有使用者輸入做驗證與長度限制
- 不可在程式碼、log 或回應中印出密碼、API key 等機密
- 密碼若需儲存，必須雜湊（bcrypt 或 werkzeug generate_password_hash）
- 錯誤訊息不可把資料庫結構或堆疊細節洩漏給使用者

# 輸出格式
- 只輸出完成這項任務需要的程式碼
- 每個函式上方加一行註解說明用途
- 需要安裝的套件列在最後

# 若需求不清楚
- 不要自行假設或捏造規格，先列出疑問問我
```

### 1.3 使用守則

- **模組化**：不要一次叫 AI 生成整個系統，逐模組生成、逐模組驗證。
- **Temperature 調低**：固定 0.2（見共用規範），確保跨批次產出一致。
- **Context 重置**：產出開始走樣或出現幻覺時，清除對話、重新載入規格，不要在壞掉的對話上硬改。

## 二、團隊角色定義

| 角色 | 主要職責 | 對應流程階段 |
|------|----------|--------------|
| **Prompt Engineer** | 需求拆解、套用標準範本撰寫指令、驅動 AI 生成、管理 Context | Vibe Coding 迴圈步驟 1–3 |
| **Reviewer** | 對照 Review Checklist 審查產出與 PR、把關功能與可讀性 | 迴圈步驟 4、PR 審查 |
| **Security Owner** | 設定並判讀安全掃描（Semgrep / GitLeaks / Trivy）、把關 Security Gate、維護 key 管理規範 | 交付後的安全掃描 |

**兩人團隊的實務分工**：本團隊兩位成員，可採「一人開 PR、另一人審」的方式輪流擔任 Prompt Engineer 與 Reviewer；Security Owner 由其中一人固定兼任，負責階段四的掃描設定與把關。重點是「生成的人不審自己的產出」。

## 三、Branch Strategy（分支策略）

採三層分支：

- **main**：永遠保持「可部署」狀態。受 Branch Protection 保護，**只能透過 PR 合併**，禁止直接 push。對應自動部署來源。
- **dev**：整合分支。各功能完成後先合進 dev 做整合測試，穩定後才開 PR 合併到 main。
- **feature/***：每個功能或模組各開一條，從 dev 切出。

### 流程

```
從 dev 切出 feature 分支
   → 在 feature 上用 Vibe Coding 開發單一模組
   → 開 PR：feature → dev（經 Reviewer 審查 + 掃描通過）
   → 整合測試穩定後，開 PR：dev → main
   → 合併進 main 觸發自動部署
```

### 命名規則

- 新功能：`feature/login`、`feature/search`
- 修錯：`fix/login-validation`
- 分支名用小寫、以 `-` 連接，描述要具體。

## 四、PR 規範與 Review Checklist

### 4.1 PR 規範

- **一個 PR 只做一件事**：對應單一模組或單一修正，避免一次塞太多變更，難以審查（也方便 TC-4 的衝突演練）。
- **PR 描述須包含**：
  - 這個 PR 做了什麼、屬於哪個模組
  - 如何測試 / 驗證（重現步驟）
  - 若對應某個測試案例，註明（如 TC-1）
- **合併條件**：
  - 至少 1 位 Reviewer 核准（開 PR 的人不能核准自己的）
  - 所有必要的狀態檢查通過（階段四掃描 workflow 完成後生效）

### 4.2 Review Checklist（審查時逐項對照）

對齊指引第 4.2 節，並補上 PR 專屬項目：

- [ ] **易讀性**：命名一致、有結構化註解
- [ ] **架構**：符合模組化、無冗餘程式碼
- [ ] **可移植性**：能在指定的 Docker / VM 環境直接運行
- [ ] **規格符合度**：完整覆蓋需求階段定義的邊界條件
- [ ] **安全性**：使用參數化查詢/ORM、有輸入驗證、無寫死機密（最終仍以自動掃描為準）
- [ ] **無機密外洩**：diff 中沒有 `.env`、API key、密碼等敏感內容
- [ ] **可測試**：本機/沙盒中功能正常、PR 描述的驗證步驟可重現
